## Findings

### 1. HIGH — real residents' document scans are committed to a public repo
`Esperanza-Mobile-App/Reference_forms/Esperanza  File/` (66 MB, 84 files) contains 18 JPEG
document scans at 1414x2000 — **11 of them are named after individual residents** and 7 are
UUID-named — plus `Certified Copy of Marriage certificate.pdf` and three
`Barangay_Certification*.pdf`. Public since commit `2811b49` (2026-08-14).

> The individual names are **withheld from this file because this repository is public** —
> naming them here would publish exactly the index this finding exists to prevent. The
> unredacted list is in the owner's local copy, `Esperanza-Mobile-SWEEP-full-2026-08-29.md`.
> `ls` the directory above to see them if you have legitimate need.

These are reference forms for building the app — they do not belong in the shipped repo at all,
let alone a public one. Removing them from `HEAD` is not enough; they stay in history and in
every existing clone/fork. Fixing this properly means history rewrite + force-push + credential
rotation-equivalent (assume they have been fetched).

### 2. HIGH — the mock "demo" identity is a real resident's record
`lib/services/mock_catalog.dart:2572` states plainly that the verified demo account is a named
resident's **actual** Constituents record from the Web Admin's own mock data — id, name, email,
birthdate, civil status, occupation, address, household and family IDs all sourced from that
record, not fabricated. The bundled demo ID images under `assets/images/` print that person's
real details, and the same pattern applies to the other two seeded demo identities.
A public demo app should ship synthetic identities. (Names withheld — see finding 1.)

### 3. HIGH — a corrupt/incompatible saved session hangs the app on the splash forever
Every service's restore path does an unguarded `jsonDecode` + `fromJson`, and no service has a
`try`/`catch` around it:

- [citizen_session_service.dart:49-63](Esperanza-Mobile/Esperanza-Mobile-App/lib/services/citizen_session_service.dart#L49-L63)
- [requests_service.dart:74-92](Esperanza-Mobile/Esperanza-Mobile-App/lib/services/requests_service.dart#L74-L92)
- also `balita_service`, `master_file_service`, `notifications_service`, `resident_profile_service`

Those `fromJson`s decode enums with `Enum.values.firstWhere(...)` and **no `orElse`**
(`service_request.dart:210`, `announcement.dart:125`, `receipt.dart:61`, `attachment.dart:86`),
so any renamed/removed enum value, or any malformed payload, throws.

The throw happens inside a future started from the constructor, so it is unhandled: `_loading`
is never set false and `notifyListeners()` never fires. `AuthGate`
([main.dart:78](Esperanza-Mobile/Esperanza-Mobile-App/lib/main.dart#L78)) then renders a
`CircularProgressIndicator` **forever**. Only clearing app data recovers it.

This is not hypothetical for this codebase — it already ships five separate migrations for
persisted data that changed shape (`_migrateStaleDemoIdentity`, `_migrateSeniorCitizenIdCategory`,
`_migrateObsoleteTrackingLabels`, ...), all of which run *after* the `fromJson` that would throw.

Fix: wrap each `_restore()` body in `try`/`catch`, fall back to empty state, and give every
enum `firstWhere` an `orElse`.

### 4. MEDIUM — status vocabulary has drifted from the web platform
Canonical list in `Esperanza-Web-Platform-frontend/CLAUDE.md` (15 statuses) vs mobile's
`lib/theme/app_status.dart` (15 statuses):

- Mobile is **missing `Resubmitted`**, which is canonical on the web side (8 files) and which
  mobile's own `requests_service.dart:964` writes into `statusHistory` as a literal string.
  It renders fine today (the timeline prints the raw label), but
  `AppStatusX.fromLabel('Resubmitted')` silently returns **`AppStatus.draft`** — so any future
  route through `fromLabel` will show a resubmitted request as grey "Draft".
- Mobile **invents `Waiting Requirements`**, which appears in **zero** files across the whole
  web platform — against the "never invent new status labels" rule both CLAUDE.mds state.
  The code knows this: `requests_service.dart:278` lists it as an *obsolete* label and migrates
  it to `Under Review` on load.
- ...yet `help_support_screen.dart:213` still tells citizens their request "may also show other
  statuses, such as Under Verification, Processing, or **Waiting Requirements**" — a status the
  app deliberately migrates away from and can no longer display. User-visible copy defect.
- `ESPERANZA_MOBILE_WEB_ALIGNMENT.md` Section 1 documents a 14-status list containing
  "Ready for Release", which exists in *neither* codebase now. The doc is stale (last updated
  2026-08-11); `app_status.dart`'s own header comment also still says "the exact 14 status names"
  for a 15-value enum.

Design tokens, by contrast, are exact: all 23 navy/brand/gold hexes in `app_colors.dart` match
`resources/css/app.css` 1:1. That part of the spec's parity claim verifies.

### 5. MEDIUM — the repo root is a second, broken Flutter project
The root holds a full Flutter scaffold (`pubspec.yaml`, `.metadata`, `analysis_options.yaml`,
`esperanza_mobile.iml`) with **no `lib/` and no `assets/`** — yet its `pubspec.yaml` declares
4 image assets and 4 font files under `assets/`. It cannot build. The real app is entirely in
`Esperanza-Mobile-App/`. Opening the repo root in an IDE or CI gives you the broken one.
`README.md`, `.metadata`, `package-lock.json` and all three screenshots are byte-identical
duplicates across the two. Left over from commit `8ea7fbe` "Merge existing Esperanza Mobile
repository with local project".

### 6. MEDIUM — `AttachmentPicker` ships in no screen, but has tests and is named in the spec
`lib/widgets/attachment_picker.dart` is the only one of 135 lib files **unreachable from
`main.dart`** (import-graph walk). It is imported solely by three test files. Section 1 of the
alignment spec names it as the shipped port of `ui/file-picker.blade.php` ("real device picker,
not a mock") and Section 9 names it as the component providing camera/gallery/PDF upload — but
the live screens use `RequirementUploader` instead. So `attachment_picker_test.dart` is green
against code no user can reach. (Document upload itself *is* wired: `requirement_uploader.dart:91`
calls `pickDocumentProtected`.)

holds real resident data. `local_auth`-style app lock is already listed as recommended-not-built
in the spec's Section 6.
